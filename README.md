# Darkflib

Personal site for the Darkflib persona: a cyberpunk interface backed by real browser telemetry, heading towards a
client-side Fault Lab (see `docs/conversation.json` for the design discussion and `docs/mockup.png` for the original
visual). React 19, Vite, and TypeScript; no CSS framework.

```sh
npm install
npm run dev          # http://127.0.0.1:5173
npm run build        # typecheck (app, worker, node) + production build to dist/
npm run preview      # serve dist/
npm run lint         # Biome lint + format check
npm run format       # apply Biome fixes
npm run test:unit    # demo engine and preset stories, headless (node --test)
npm run test:e2e     # build, then Playwright across Chromium, Firefox, and WebKit
npm run pages        # regenerate projects/, demos/**, login/** and tools/** index.html from their sources
npm run images       # regenerate public/images from assets/source
npm run kev          # fetch a real KEV snapshot into .feeds/ (needs SRETAB_PAT in .env, and Go)
npm run fonts        # rebuild the Rajdhani files with corrected glyph bounding boxes (needs uv)
```

Playwright browsers are a one-off `npx playwright install chromium firefox webkit`.

Production image, locally (Docker or Podman):

```sh
docker build -f Containerfile --build-arg BUILD_SHA="$(git rev-parse HEAD)" -t darkflib.com:ci .
CONTAINER_ENGINE=docker KEEP=1 deploy/scripts/smoke.sh     # routes, headers, cache policy, hardening
npx playwright test -c playwright.deploy.config.ts         # browser check against that container
docker rm -f darkflib-smoke
```

## Telemetry strip

Every value in the strip under the hero is read from the browser or the build, never simulated:

| Item      | Source                                                                                         |
| --------- | ---------------------------------------------------------------------------------------------- |
| `SW`      | Service worker store: controlling, starting, failed, off, or unsupported; flags waiting updates |
| `BUILD`   | Commit SHA baked in at build time (`*` = dirty tree); build time in the tooltip                |
| `PROTO`   | `nextHopProtocol` of the document's navigation timing                                          |
| `EDGE`    | nginx cache status via `Server-Timing: edge`: HITs among subresources that crossed the network (`LOCAL` if all came from the browser cache, whose replayed headers are ignored; `—` with no edge) |
| `TTFB`    | `responseStart` of the navigation, plus `(CACHE)` when no bytes were transferred               |
| Bars      | Resource Timing for the last 62 subresource requests: log-scaled, dim when cached, magenta ≥ 800 ms |
| `FPS`     | Frames rendered in the last second, counted with `requestAnimationFrame`; magenta below 30     |
| `UTC`     | Wall clock, ticking on the second; hidden below 800 px wide, where only `LOCAL` fits           |
| `LOCAL`   | The same clock in the browser's time zone, which the tooltip names                             |

The bars will pick up Fault Lab latency injection with no extra wiring, since injected delays show up in Resource
Timing.

The footer is `position: sticky` at the bottom of the window. Being in flow, it sits below the last panel at the end of
the page rather than covering it, and `scroll-padding-bottom` keeps scrolled-to and focused elements clear of it. The
shell uses `overflow: clip`, since `hidden` would make it the footer's scroll container.

## Fault Lab

A `FAULT_LAB` section below the dashboard lets a visitor break things and watch the page recover. Everything happens in
their own browser: the service worker injects faults into that tab's requests only, and the origins stay healthy for
everyone else.

- **The system under test** (`src/lab/statusClient.ts`) polls a status document from `api.darkflib.com`, fails over to
  `api.darkflib.dev` (a different registrable domain, so genuinely cross-site), and probes `media.darkflib.com`. It
  applies per-attempt timeouts, retries with exponential backoff and full jitter, honours `Retry-After` (waiting out
  short ones, and backing off entirely for long ones), opens a circuit breaker per origin after consecutive failures,
  and serves the last good data when both APIs are down. It never talks to the worker: faults reach it only as failed
  requests.
- **The fault engine** (`src/sw/fault-engine.ts`) holds rules per tab and answers only matching requests: `offline`
  (network error, no request sent), `latency` (a delay, then the real request), and `status` (a synthetic 429 or 503 with
  `Retry-After`, no request sent), each with a probability. It refuses the site's own origin and never touches page
  loads, so the lab cannot break the page that runs it.
- **Control** (`src/lab/faultControl.ts`) sends `fault:set` and shows what the worker acknowledged, not what it sent.
  Rules live in worker memory, so it re-sends them when a batch arrives from a new worker instance (restarted or
  replaced). The panel stays disabled, and says why, unless the controlling worker reports `fault-injection`.
- **Observability:** the event log's `FAULT` rows (injections) and `CLIENT` rows (retries, circuit changes, failover,
  state) form one timeline, and the lab's polls feed the strip's latency bars. `EDGE` counts same-origin requests only.
- **Origins** serve static JSON from `lab/origins/` through the same Caddy image, with CORS and `Timing-Allow-Origin` for
  the site and `no-store`. `/lab/config.json` lists them, along with the client's timings; `enabled: false` switches
  polling off. The CSP's `connect-src` must list the same origins, and `smoke.sh` checks that it does.

`tests/e2e/fault-engine.spec.ts` drives the worker directly: each mode, what reaches the origin (counted by the test
server's stand-in origins), clearing, rejections, and per-tab scope. `tests/e2e/fault-lab.spec.ts` drives the panel:
failover, circuit open, half-open, and close, stale data, Retry-After handling, timeouts, reset, the outdated-worker
state, and re-sending rules after a worker restart (Chromium only, since stopping a worker needs DevTools). The test
server shortens the client's clock through the config, and enables polling only for these tests.

## Known exploited vulnerabilities

A `KNOWN_EXPLOITED` panel lists what CISA has seen exploited in the wild, taken from
[sre-tab](https://github.com/Darkflib/sre-tab), which already ingests the KEV catalogue. sre-tab's API needs a
credential, so the browser never talks to it: `kev-snapshot` (in the site's own image) runs hourly on the server,
pages through `/api/v1/feed?sources=cisa-kev` with a read-only PAT, and writes `kev.json` to a volume Caddy serves as
`/feeds/kev.json`. Visitors fetch one static file from this origin, and no request of theirs reaches sre-tab.

- **The snapshot carries only what a visitor sees.** The feed item's `read` and `bookmarked` flags are the token
  owner's reading history, and the fetcher never copies them. It keeps the CVE, the name, the description, the date
  added, and the deadline and ransomware flag it splits back out of sre-tab's summary text, plus CISA's own link when
  it is https on `www.cisa.gov`. `src/kev/snapshot.ts` re-checks all of that in the browser: this is a document from
  the network, whoever wrote it.
- **Failure is a missing panel, never a broken one.** A failed refresh leaves the previous file in place, so the page
  shows the last good data with its age; past three hours it is marked `STALE`, and past a week the panel hides
  itself. An empty volume — a first deploy, or a host with no PAT — is a 204, which keeps the console clean.
- **The numbers are relative to the snapshot, not to the reader's clock**: the 7-, 30- and 90-day counts and the
  13-week histogram describe the file, so they stay honest whatever its age or the browser's time zone.

`tests/e2e/kev.spec.ts` covers the rendered snapshot, opening an entry, showing all of it, the stale marker, and each
way the panel hides itself. `kev-snapshot/snapshot_test.go` covers the fetch and the transform, including that no
reader state survives it; both run in CI, the Go tests inside the image build.

## Private tools

Some tools cost credits or touch a service agreement, so they live behind a login at `/tools/*`. Sign-in is
[wwff-auth](https://github.com/Darkflib/wwff-auth) (private repo), a separate service this site's Caddy reaches as
`wwff-auth:8000` on darkflib.network; its API is that repo's `docs/contract.md`, and it is deployed as the gitops app
`quadlet/apps/wwff-auth/`. This repository holds the pages and the routing.

```
browser ── /login/, /login/enrol/      static pages here (src/login/), talking to /auth/* with fetch
        ── /auth/*                     Caddy → wwff-auth (never stored; /auth/verify is a 404 from outside)
        ── /tools/*                    Caddy forward_auth → wwff-auth /auth/verify, then the tool
```

- **Signing in.** Invite-only: Mike runs `wwff-auth invite` on ny03 and sends the `/login/#invite=…` link it prints.
  The page redeems the token once and drops it from the address bar, then the visitor signs in with GitHub or Google
  and is sent to `/login/enrol/` to add a passkey. Returning visitors can use either provider or the passkey.
  `?next=` is resolved as a URL and must stay on this origin; anything else goes to `/tools/`.
- **The gate.** Every `/tools/*` request asks `/auth/verify` first, which checks `/tools/<slug>/` against that tool's
  roles (below) and `/tools/` itself against the session alone. For page loads Caddy turns the refusals into pages:
  no session → `/login/?next=<path>`; a role held but not proven recently enough (the step-up 401, told apart by its
  `WWW-Authenticate: Passkey` header) → `/login/step-up/?next=<path>`, which asks for that proof and goes on to the
  tool; no role for the tool → `/login/denied/`. Anything else gets the response as is. Allowed requests go on
  carrying `X-Auth-User`, `X-Auth-Level`, `X-Auth-Federated-At` / `-Standard-At` / `-High-At` (Unix seconds, absent
  where that level doesn't count now), `X-Auth-Roles` (active roles) and `X-Auth-Tool`. Client-sent `X-Auth-*`
  headers are stripped first, inside a `route` block, because Caddy's default order runs `forward_auth` before
  `request_header`. Gated responses, refusals included, are `private, no-store`.
- **Levels and roles.** `FEDERATED` is GitHub or Google, `STANDARD` any passkey, `HIGH` a hardware key that passed
  FIDO MDS3 attestation. A **role** (`admin`, `user`) is granted to a user and is **active** while the session has
  proven the role's level within its `max_age`. Each tool lists the roles that open it (any of them); a tool that
  isn't listed is refused. Both live in wwff-auth's access file, `quadlet/apps/wwff-auth/files/access.toml` in
  wwff-tech/gitops, so raising `admin` to `HIGH` once the YubiKey is enrolled is a one-line PR there. `/tools/` lists
  only the tools the user holds a role for (`GET /auth/tools`), marking those that need a step-up first.
- **Keys.** `/login/enrol/` adds an ordinary passkey or, with ADD A HARDWARE KEY, asks for `HIGH`; the service grants
  `HIGH` only to a non-syncing, attested security key, and only after a first-day cooldown. The result says which
  tier the key got and why.
- **Second provider.** The session debugger's Linked accounts panel links GitHub to Google (or back) and unlinks them,
  running the passkey step-up the service requires first. By hand: step up, then within five minutes open
  `/auth/<provider>/start?link=1&next=/tools/debug/`. Accounts are never matched by email.

### Adding a tool

- **Who may open it**: add `[tools.<slug>]` with its `roles` (and, if it spends credits, its `credits` types) to the
  access file in gitops. Until then the gate refuses it to everyone.
- **A page with no backend**: add it to `accessPages()` in `scripts/pages.ts` (unlisted, so `noindex` and out of the
  sitemap), a key in `src/login-main.tsx`, an input in `vite.config.ts`, and an entry in `TOOLS` in
  `src/login/tools.ts` (its name and blurb on `/tools/`). `/tools/*` is gated as a whole, so nothing in the Caddyfile
  changes.
- **A tool with a backend**: route its path inside the `/tools/*` `route` block in `deploy/Caddyfile`, after
  `forward_auth` and before `file_server` (`reverse_proxy` to a container on darkflib.network), and run that container
  from gitops so nothing but Caddy can reach it: the backend trusts the `X-Auth-*` headers only because of that.
  Check them per action with wwff-auth's `contrib/python` helpers (copied in, not installed): `require` for a level
  and age, `require_role` for a role; both answer as the service would. The page calls the backend through wwff-auth's
  `contrib/ts` `fetchWithStepUp`, which runs the passkey prompt on a step-up 401 and retries once. A backend that
  spends credits calls wwff-auth's `/internal/credits/spend` (and `/refund` when a run fails upstream) directly, with
  its own tool token; see wwff-auth's `docs/operations.md`.
- Add the route's checks to `deploy/scripts/smoke.sh` alongside the existing gate checks, and teach the stand-in
  (`deploy/scripts/auth-stub.Caddyfile`) any new answers it needs.

### User admin

`/tools/users/`, gated to `admin`. Search users (email, name, GitHub or Google login, or id), open one to see their
accounts, passkeys, roles and credits, toggle the roles the access file marks `web_grantable` (`admin` is never one:
it's granted only with `wwff-auth roles grant` on the server), and add or remove credits of each type with a note.
The page calls wwff-auth's `/auth/admin/*` API, which checks `admin` itself on every call; once `admin` lapses
mid-session, the page asks for the step-up on the next click and repeats the action. Every change is audited by the
service.

### Credits

Credit types (e.g. `domain`) are defined in the access file. Each user has a balance per type, never negative, and an
append-only history; admins adjust them in `/tools/users/`, tools spend them through wwff-auth's internal API, and
users see their own balances on `/tools/` and in the session debugger.

### Domain recon

`/tools/domain/`, for the `user` role: registration (RDAP, or WHOIS where a registry has none), DNS (delegation
trace, records, DNSSEC, CAA), TLS (chain, versions, SCTs, OCSP), HTTP headers, and Certificate Transparency (every
certificate the CT logs hold for the name and its subdomains: issuers, the names they reveal, and whether current
issuers are ones the CAA records allow) for a domain, collected live by
[wwff-recon](https://github.com/Darkflib/wwff-recon) (private) with
[domaincheck](https://github.com/wwff-tech/domain-check), and crt.sh (or Cert Spotter) for CT. Caddy proxies `/tools/domain/api/*` to the `wwff-recon`
container inside the gate, so it gets the same `X-Auth-*` headers; the service checks `user` itself, spends one
`domain` credit per run through wwff-auth, and refunds it when every check failed for an upstream reason. The page
shows a summary per check (each row marked good, worth a look, or bad, from `src/login/reconView.ts`), the findings
that deserve attention above them, the full `domaincheck` result under each, the balance, and the recent runs; the
shown run is in the address bar (`?run=`) so a reload reopens it while the service keeps it (90 days, in a SQLite
file on wwff-recon's volume). Any run can be compared with another from the newest 100 (the same domain over time, or
two domains): `src/login/reconCompare.ts` lines up the summary rows side by side, marks the ones that changed and the
findings that appeared or cleared, with the raw JSON difference under it, and the pair is in the address bar too
(`?run=…&vs=…`). A run downloads as its JSON, or as a report (`src/login/reconReport.ts`): one HTML file with the
findings, the summaries, and SVG diagrams of the DNS delegation, the certificate chain, and the redirects. It has no
script and a CSP of its own that forbids any request, and it prints to PDF. Both work off rows, so a row added to
`reconView.ts` shows up in the comparison and the report unchanged. Its API is wwff-recon's `docs/contract.md`. Being its own container, wwff-recon can later queue runs or collect from several
points of presence behind the same API.

### Page recon

`/tools/page/`, for the `user` role: one URL loaded in headless Chromium by
[wwff-pagerecon](https://github.com/Darkflib/wwff-pagerecon) (private), as a visitor's browser would, so it's an active
scan with its own `page` credits, separate from domain recon's. A run reports a screenshot, metadata (meta tags, Open
Graph, Twitter cards, JSON-LD), structure (headings, landmarks, word count), links (same-origin ones checked), styles
and fonts, images, Navigation/Paint/LCP/CLS timings, the document's headers, every request the page made (type,
status, size, host, third party or not), the libraries and versions it exposes, the CSP in effect, and an
accessibility audit (axe-core's WCAG 2.2 rules, summarised here and read in full by `/tools/a11y/`). The page
(`src/login/PageReconPage.tsx`) shows the findings first (no CSP or a weak one, no Open Graph, missing alt text, mixed
content, heavy third parties, outdated or exposed library versions, slow LCP, …, from `src/login/pageView.ts`, which
is unit-tested), then a summary per section, then the full data in tables and as JSON. Caddy proxies
`/tools/page/api/*` to the `wwff-pagerecon` container inside the gate, as for domain recon; the service checks `user`
itself, spends one `page` credit per run, and refunds it when the page didn't load for a reason on the other side.
Screenshots are served by the service under the same path, so `img-src 'self'` allows them. Every connection the
browser makes goes through an egress proxy in the service that refuses internal addresses; its API, limits and SSRF
policy are wwff-pagerecon's `docs/contract.md`.

### Accessibility

`/tools/a11y/`, for the `user` role (`src/login/A11yPage.tsx`, its maths in `src/login/a11y.ts`, unit-tested). A
contrast checker: two colours (hex, `rgb()`, `hsl()` or a CSS name), the WCAG 2 ratio as WCAG reads it (truncated,
never rounded up), a pass or fail for each of 1.4.3, 1.4.6 and 1.4.11, the nearest colours that pass (same hue, the
text or the background moved), the pair as each kind of colour-vision deficiency sees it, and APCA's Lc for
reference; the pair is in the address bar (`?fg=…&bg=…`). A palette grid of every pair from up to 24 colours. Both
run in the browser and cost nothing. A page audit is a page recon run, so it spends a `page` credit and is gated as
page recon's API: the page shows the run's `accessibility` section (violations worst first with their WCAG criteria
and the elements, each failing colour pair with a fix and a button that loads it into the checker, what needs a
person to review), and links to the rest of the run on `/tools/page/`. The access file lists `[tools.a11y]` with no
credits of its own.

### The session debugger

`/tools/debug/` is the first tool and a placeholder: the session as `/auth/session` reports it (each level's proof
time, with live ages), the `X-Auth-*` headers a tool behind the gate receives, example requirements checked against
them, the enrolled passkeys, linked accounts with link and unlink, and passkey and hardware-key step-ups that refresh
all of it. Caddy answers `/tools/debug/headers.json` itself, inside the gate, by echoing the forwarded headers, so it
needs no backend.

### Locally

`AUTH_ORIGIN=http://localhost:8000 npm run dev` proxies `/auth` to a local wwff-auth (its README covers running one).
Without it `/auth` is a 404 and the pages behave as signed out. The Vite dev server does not gate `/tools/*`; only
Caddy does, so check the gate against the production image: `smoke.sh` runs `deploy/scripts/auth-stub.Caddyfile` in a
second container as a stand-in for wwff-auth (the cookie `smoke=1` is a session), and checks the redirect, the 401,
the stripped headers (the check fails if the strip is removed), the cache headers, and the debugger's echo. The
deploy browser test then loads `/login/`, `/tools/`, and `/tools/debug/` signed out and signed in, with no CSP
violations or console errors. Passkey prompts need a secure origin, so step-ups are only exercised on darkflib.com.

## Service worker

`src/sw/service-worker.ts` is bundled by `build/serviceWorkerPlugin.ts` with esbuild into a single classic script at
`/service-worker.js`: a stable URL, with no content hash, outside Vite's module graph. Dev serves a fresh bundle per
request, so editing the worker exercises the browser's real update flow. The worker's version is `sw-<hash>`, a hash
of its own bundle; the commit SHA and build time are deliberately left out. A deploy that does not touch the worker
therefore serves identical bytes, and browsers find no update. The panel shows that version, and the strip's `BUILD`
shows the page's commit; the two are independent.

Current scope: registration, lifecycle observation, control detection, a `MessageChannel` version handshake, and a
**passive fetch observer**, all feeding one bounded, emit-ordered event log. The worker never calls `skipWaiting()` by
itself: an update waits until no page uses the old worker, or until a visitor presses **UPGRADE** in the panel.

- When an update is waiting, the page runs the version handshake with it too, and the panel shows its version. The
  button is enabled only if that worker reports `skip-waiting`. Pressing it sends `sw:skip-waiting` to the waiting
  worker, which calls `skipWaiting()` and takes over every open tab. Each tab sees `controllerchange` and repeats the
  handshake. The worker serves nothing from a cache, so a page from an older deploy keeps working under the new
  worker. Fault Lab rules lived in the old worker's memory, so each tab re-sends its own once the new controller has
  answered. If the worker has not activated after 10 s, the button can be pressed again.

The fetch listener never calls `respondWith`, so the browser performs every request exactly as it would without the
worker; responses, Resource Timing, and the strip's `EDGE` and latency bars are unaffected. It records method, URL,
destination, and mode, batches them for 50 ms, and delivers each batch only to the tab that made the requests. A
page load's own row waits in the worker until its new page exists. Status and timings come from the page's Resource
Timing rather than the worker.

- A fetch listener routes every page load through the worker. When the worker is already running the cost measured
  sub-millisecond locally; a worker woken from idle costs more. The strip's `TTFB` tooltip shows the startup time
  (`fetchStart - workerStart`) for each visit, so it is measured on real page loads rather than assumed.
- Log rows are tagged `LIFECYCLE`, `CONTROL`, or `FETCH`, and each tag can be hidden (remembered per browser). When
  the log is full, request rows are dropped before lifecycle and control history.
- `startServiceWorker()` runs at module load in `main.tsx`, so the message listener exists before the page's message
  queue opens; registration still waits for `load`, and happens in dev as well as production.
- `?sw=off` unregisters every registration for the origin and skips registering. Use it to clear a stale worker
  locally.
- Serve `/service-worker.js` with `Cache-Control: no-cache` in production. The page also registers with
  `updateViaCache: 'none'`.

`tests/e2e/service-worker.spec.ts` covers first visit (control without reload), reload (no reinstall), update (new
worker waits, old keeps control, takeover after the last tab closes), upgrading from the panel, multiple tabs, and
the kill switch. The test
server can serve a byte-different worker on demand to drive the update cases. `tests/e2e/fetch-observer.spec.ts`
covers passivity (the network answers), the page-load row, per-tab delivery, tag filtering, and eviction order.

Playwright's patched Firefox leaves a page uncontrolled after a navigation that the worker observes without
responding; real Firefox keeps it controlled, as the spec requires (checked against Developer Edition with
puppeteer-core). Tests that depend on a worker-routed navigation therefore skip the Firefox project; the rest,
including first-visit observation, run in all three engines.
